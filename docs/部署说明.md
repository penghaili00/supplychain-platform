# SupplyChain 在 WSL 与远程 Linux 的部署说明

## 目标

这份文档的目标是把 SupplyChain 的日常运行方式切到 Linux 优先，让同一套命令可以同时适用于：

- WSL
- 本机 Linux
- 远程 Linux 服务器

调整完成后，日常的拉取容器、启动基础设施、导入 Nacos、打包、启动服务都不再依赖 PowerShell。
本地默认环境入口也统一收口到 `deploy/env/local.env`。

## 本次补充的内容

- 新增 `scripts/linux/*.sh`，统一处理 Compose、Nacos 导入、打包、服务启停
- 新增 `deploy/env/*.env.example`，作为本地、开发、生产三套环境模板
- 将部分原来写死在 `nacos/*.yml` 里的值改为环境变量占位：
  - MySQL 数据库名
  - 各模块端口
  - Dubbo 端口
  - 定时任务 cron
  - MQ 启用开关

## 推荐的多环境方案

当前项目不建议把 `spring.profiles.active` 当成主环境隔离手段。
更适合现在这套架构的方式是：

1. 每个环境一份独立的 `env` 文件
2. 每个环境一个独立的 Nacos namespace
3. 同一组 Data ID 导入到不同 namespace

推荐映射关系：

| 环境 | Env 文件 | Nacos namespace |
| --- | --- | --- |
| local | `deploy/env/local.env` | `supplychain_local` |
| dev | `deploy/env/dev.env` | `supplychain_dev` |
| prod | `deploy/env/prod.env` | `supplychain_prod` |

这样做的好处是：

- MySQL、Redis、Nacos、RabbitMQ、ES 的地址和密码都交给环境变量管理
- 业务共享配置仍然沿用 `nacos/*.yml`
- 同一份配置源可以导入到不同 namespace
- 如果某个值有明显环境差异，优先改成 `${SUPPLYCHAIN_*}` 占位，不再手写死

本地场景请统一遵守下面这个约定：

- 默认只认 `deploy/env/local.env`
- 不再使用项目根目录 `.env`
- 日常不要直接手敲裸 `docker compose ...`
- 本地基础设施统一走 `./scripts/linux/compose.sh` 或 `./scripts/linux/bootstrap.sh`

## 配置应该改哪里

### 1. 适合放在 Env 文件里的配置

这些值通常应该放在 `deploy/env/*.env` 中维护：

- 基础设施地址：
  - `SUPPLYCHAIN_MYSQL_HOST`
  - `SUPPLYCHAIN_REDIS_HOST`
  - `SUPPLYCHAIN_NACOS_ADDR`
  - `SUPPLYCHAIN_RABBITMQ_HOST`
  - `SUPPLYCHAIN_ES_URL`
- 账号密码与密钥：
  - `SUPPLYCHAIN_MYSQL_USERNAME`
  - `SUPPLYCHAIN_MYSQL_PASSWORD`
  - `SUPPLYCHAIN_NACOS_PASSWORD`
  - `SUPPLYCHAIN_JWT_SECRET`
  - `SUPPLYCHAIN_APP_SIGN_SECRET`
- 数据库名：
  - `SUPPLYCHAIN_MYSQL_DATABASE`
- Nacos 环境标识：
  - `SUPPLYCHAIN_NACOS_NAMESPACE`
  - `SUPPLYCHAIN_NACOS_NAMESPACE_NAME`
  - `SUPPLYCHAIN_NACOS_GROUP`
- 各模块运行端口：
  - `SUPPLYCHAIN_SERVICE_PROVIDER_PORT`
  - `SUPPLYCHAIN_ADMIN_PORT`
  - `SUPPLYCHAIN_API_PORT`
  - `SUPPLYCHAIN_GATEWAY_PORT`
  - `SUPPLYCHAIN_TASK_PORT`
  - `SUPPLYCHAIN_MQ_PORT`
- Dubbo 端口：
  - `SUPPLYCHAIN_DUBBO_PORT`
- 任务调度：
  - `SUPPLYCHAIN_TASK_DEMO_CRON`
- MQ 是否启用：
  - `SUPPLYCHAIN_RABBITMQ_ENABLED`

### 2. 适合继续放在 Git 里的 Nacos 配置源

下面这些文件仍然应该作为 Git 内维护的配置源：

- `nacos/datasource.yml`
- `nacos/redis.yml`
- `nacos/dubbo-provider.yml`
- `nacos/dubbo-consumer.yml`
- `nacos/jwt.yml`
- `nacos/management.yml`
- `nacos/supplychain-*.yml`

推荐约定：

- 会随着环境变化的值，尽量写成 `${SUPPLYCHAIN_*}` 占位
- 所有环境都相同的值，直接写在 `nacos/*.yml`
- 只有某个特殊环境才不同、又不适合参数化的值，可以在该环境对应的 namespace 中单独修改，但最好把原因补回文档

## 现在这套配置的关键点

### Nacos

现在所有服务都通过 `bootstrap.yml` 接入 Nacos，核心控制项是：

- `SUPPLYCHAIN_NACOS_ADDR`
- `SUPPLYCHAIN_NACOS_USERNAME`
- `SUPPLYCHAIN_NACOS_PASSWORD`
- `SUPPLYCHAIN_NACOS_NAMESPACE`
- `SUPPLYCHAIN_NACOS_GROUP`

如果你的 Nacos 中“命名空间展示名”和真实 `namespaceId` 不一致：

- `SUPPLYCHAIN_NACOS_NAMESPACE` 必须填写真实 `namespaceId`
- `SUPPLYCHAIN_NACOS_NAMESPACE_NAME` 可以填写展示名，供导入脚本使用

### MySQL

现在 `nacos/datasource.yml` 已经改成使用下面这组变量：

```yaml
${SUPPLYCHAIN_MYSQL_HOST}
${SUPPLYCHAIN_MYSQL_PORT}
${SUPPLYCHAIN_MYSQL_DATABASE}
${SUPPLYCHAIN_MYSQL_USERNAME}
${SUPPLYCHAIN_MYSQL_PASSWORD}
```

也就是说，切换数据库环境时不再需要手动改 JDBC URL，只改对应环境文件即可。

### Elasticsearch

Elasticsearch 当前通过下面这组变量接入：

- `SUPPLYCHAIN_ES_URL`
- `SUPPLYCHAIN_ES_USERNAME`
- `SUPPLYCHAIN_ES_PASSWORD`

本地 compose 现在已经内置 Elasticsearch 单节点服务，默认映射到宿主机 `9200` 端口。

### RabbitMQ

RabbitMQ 这里要特别注意分成两组变量：

- Compose 侧端口映射：
  - `SUPPLYCHAIN_RABBITMQ_AMQP_PORT`
  - `SUPPLYCHAIN_RABBITMQ_HTTP_PORT`
- 应用侧连接配置：
  - `SUPPLYCHAIN_RABBITMQ_HOST`
  - `SUPPLYCHAIN_RABBITMQ_PORT`
  - `SUPPLYCHAIN_RABBITMQ_ENABLED`

如果你只改了容器映射端口，但没有同步改应用侧变量，`supplychain-mq` 仍然会连旧地址。

## 新增脚本说明

| 脚本 | 作用 |
| --- | --- |
| `scripts/linux/compose.sh` | Linux 下的 `docker compose` 包装脚本 |
| `scripts/linux/bootstrap.sh` | 启动基础设施并导入 Nacos 配置 |
| `scripts/linux/import-nacos.sh` | 把 `nacos/*.yml` 导入指定 namespace/group |
| `scripts/linux/build.sh` | Maven 打包 |
| `scripts/linux/run-service.sh` | 启动单个服务 |
| `scripts/linux/start-all.sh` | 按顺序启动整套服务 |
| `scripts/linux/stop-all.sh` | 停止单个或全部本地服务 |

## 一次性准备

### WSL 或 Linux 主机需要安装

至少需要：

- JDK 21
- Maven 3.9+
- Docker Engine 或 Docker Desktop 的 WSL 集成
- Docker Compose 插件
- `curl`

可选但推荐：

- `lsof`
- `vim` 或 `nano`

### 准备环境文件

可以先从模板复制：

- `deploy/env/local.env.example`
- `deploy/env/dev.env.example`
- `deploy/env/prod.env.example`

建议命令：

```bash
cp deploy/env/local.env.example deploy/env/local.env
cp deploy/env/dev.env.example deploy/env/dev.env
cp deploy/env/prod.env.example deploy/env/prod.env
```

然后把里面的地址、账号、密码、密钥全部改成真实值。

如果你只是本地跑项目，至少要先准备好：

```bash
cp deploy/env/local.env.example deploy/env/local.env
```

## 在 WSL 本地运行

### 1. 拉取基础镜像

```bash
./scripts/linux/compose.sh pull
```

### 2. 启动基础设施并导入 Nacos

```bash
./scripts/linux/bootstrap.sh --pull-first
```

这个脚本会完成：

- 启动 MySQL、Redis、Elasticsearch、Nacos、RabbitMQ
- 等待端口与 Nacos HTTP 就绪
- 把 `nacos/*.yml` 全部导入当前配置的 namespace

### 3. 打包项目

```bash
./scripts/linux/build.sh
```

只打某一个模块时：

```bash
./scripts/linux/build.sh --module supplychain-gateway
```

### 4. 启动 Java 服务

启动整套服务：

```bash
./scripts/linux/start-all.sh
```

连 MQ 一起启动：

```bash
./scripts/linux/start-all.sh --with-mq
```

只启动一个服务：

```bash
./scripts/linux/run-service.sh --service supplychain-gateway
```

前台排障模式：

```bash
./scripts/linux/run-service.sh --service supplychain-service-provider --foreground
```

### 5. 停止服务

停止全部：

```bash
./scripts/linux/stop-all.sh
```

只停某一个：

```bash
./scripts/linux/stop-all.sh supplychain-gateway
```

## 在远程 Linux 服务器运行

### 方案 A：中间件和 Java 服务都部署在同一台服务器

1. 把仓库上传或拉到服务器
2. 准备好 `deploy/env/prod.env`
3. 启动中间件并导入 Nacos：

```bash
./scripts/linux/bootstrap.sh --env-file deploy/env/prod.env --pull-first
```

4. 打包：

```bash
./scripts/linux/build.sh --env-file deploy/env/prod.env
```

5. 启动服务：

```bash
./scripts/linux/start-all.sh --env-file deploy/env/prod.env --with-mq
```

### 方案 B：MySQL / Redis / Nacos / RabbitMQ 由其他服务器提供

如果基础设施已经独立部署好了，只需要：

1. 在 `deploy/env/prod.env` 中填好真实地址
2. 跳过本机 compose 启动，仅检查连接并导入 Nacos：

```bash
./scripts/linux/bootstrap.sh --env-file deploy/env/prod.env --skip-compose-up
```

3. 打包并启动：

```bash
./scripts/linux/build.sh --env-file deploy/env/prod.env
./scripts/linux/start-all.sh --env-file deploy/env/prod.env --with-mq
```

## 新增一个环境时怎么做

以 `sit` 环境为例：

1. 复制一份环境模板：

```bash
cp deploy/env/dev.env.example deploy/env/sit.env
```

2. 修改 `sit.env` 中所有 `SUPPLYCHAIN_*` 地址、账号、密码
3. 设置新的 Nacos namespace：

```bash
SUPPLYCHAIN_NACOS_NAMESPACE=supplychain_sit
SUPPLYCHAIN_NACOS_NAMESPACE_NAME=supplychain_sit
```

4. 导入这个环境的 Nacos 配置：

```bash
./scripts/linux/bootstrap.sh --env-file deploy/env/sit.env --pull-first
```

如果中间件是外部提供的，也可以只导入：

```bash
./scripts/linux/import-nacos.sh --env-file deploy/env/sit.env
```

## 如何修改 MySQL 配置

如果只是切换某个环境的数据库，不需要去改源码，只改对应环境文件即可：

```bash
SUPPLYCHAIN_MYSQL_HOST=10.20.30.40
SUPPLYCHAIN_MYSQL_PORT=3306
SUPPLYCHAIN_MYSQL_USERNAME=supplychain_sit
SUPPLYCHAIN_MYSQL_PASSWORD=ChangeMe
SUPPLYCHAIN_MYSQL_DATABASE=supplychain_sit
```

改完后建议重新导入 Nacos，再重启 `supplychain-service-provider`：

```bash
./scripts/linux/import-nacos.sh --env-file deploy/env/sit.env
./scripts/linux/stop-all.sh supplychain-service-provider
./scripts/linux/run-service.sh --env-file deploy/env/sit.env --service supplychain-service-provider
```

## 如何修改 Nacos 目标环境

只需要修改对应环境文件里的这几项：

```bash
SUPPLYCHAIN_NACOS_ADDR=10.20.30.50:8848
SUPPLYCHAIN_NACOS_NAMESPACE=supplychain_sit
SUPPLYCHAIN_NACOS_NAMESPACE_NAME=supplychain_sit
SUPPLYCHAIN_NACOS_GROUP=DEFAULT_GROUP
```

然后重新导入：

```bash
./scripts/linux/import-nacos.sh --env-file deploy/env/sit.env
```

## 推荐启动顺序

推荐顺序仍然是：

1. `supplychain-service-provider`
2. `supplychain-admin`
3. `supplychain-api`
4. `supplychain-gateway`
5. `supplychain-task`
6. `supplychain-mq`

`start-all.sh` 已经按这个顺序执行。

## 日志与 pid 文件位置

Linux 脚本会把运行文件放到：

- 日志目录：`.runtime/logs/`
- pid 目录：`.runtime/pids/`

例如：

- `.runtime/logs/supplychain-gateway.log`
- `.runtime/pids/supplychain-gateway.pid`

## 常见问题排查

### 1. Nacos 导入失败

优先检查：

- `SUPPLYCHAIN_NACOS_ADDR`
- `SUPPLYCHAIN_NACOS_USERNAME`
- `SUPPLYCHAIN_NACOS_PASSWORD`
- `SUPPLYCHAIN_NACOS_NAMESPACE`
- 当前 Nacos 是否开启了鉴权

如果 namespace 展示名和真实 ID 不一致，要先修正 `SUPPLYCHAIN_NACOS_NAMESPACE`。

### 2. 服务启动了，但读取到的配置不对

最常见的原因有：

- 用错了 env 文件
- 连接到了错误的 Nacos namespace
- `group` 不一致
- 改了 `nacos/*.yml`，但没有重新导入

### 5. 为什么现在不用根目录 `.env`

现在脚本默认会读取 `deploy/env/local.env`，`docker compose` 包装脚本也会显式把这个文件传给 Compose。

这样做的目的是：

- 避免根目录 `.env` 和多环境文件并存，造成歧义
- 避免你以为改的是本地配置，实际 Compose 读到的是另一份旧文件
- 让本地、开发、生产三套环境文件保持同一目录结构

### 3. Gateway 转发不到下游

优先检查：

- `supplychain-service-provider`、`supplychain-admin`、`supplychain-api` 是否注册到同一个 Nacos namespace
- `supplychain-gateway` 使用的 `SUPPLYCHAIN_NACOS_NAMESPACE` 是否一致
- 端口变量和 Nacos 中的模块配置是否一致

### 4. MQ 模块连不上 RabbitMQ

同时检查：

- `SUPPLYCHAIN_RABBITMQ_HOST`
- `SUPPLYCHAIN_RABBITMQ_PORT`
- `SUPPLYCHAIN_RABBITMQ_ENABLED=true`

## 后续更推荐补上的能力

这次已经把 WSL / Linux / 远程服务器的基础运行链路打通了。如果后面要继续往生产可维护性上走，建议下一步补：

1. 每个服务的 `systemd` unit
2. 把密钥从明文 env 文件迁到更安全的密钥管理方式
3. 网关前增加反向代理和 HTTPS
4. 给 `.runtime/logs` 加日志轮转
5. 视情况把 Java 服务也容器化
