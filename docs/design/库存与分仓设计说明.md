# B2B 供应链订单履约平台库存与分仓设计说明

## 1. 文档目标

本文档用于定义一期订单履约中的库存查询、库存锁定、库存释放、库存扣减以及基础分仓规则，为后续库存表设计、服务实现和任务补偿提供统一约束。

一期的目标不是实现复杂智能调度，而是先把“库存一致性 + 基础仓库分配 + 可追踪流水”做扎实。

## 2. 设计范围

本文档覆盖以下内容：

- 库存对象与库存口径
- 下单审核后的库存锁定规则
- 基础分仓规则
- 锁库失败与取消释放规则
- 出库后的库存扣减规则
- 与订单状态机、出库发货流程的衔接方式

本文档暂不覆盖：

- 多仓最优路径算法
- 复杂拆单策略
- 调拨单
- 采购回补
- 安全库存预警任务实现细节

## 3. 一期设计原则

- 库存以 `仓库 + SKU` 为最小管理单元
- 可售库存与锁定库存必须分离
- 锁库动作必须有记录，不能只修改数量
- 分仓规则一期从简，优先保障流程稳定
- 锁库、释放、扣减都必须落库存流水
- 分仓结果要能回溯到订单明细，便于后续拆单扩展

## 4. 库存核心概念

### 4.1 现有库存口径

一期建议采用以下库存口径：

- `on_hand_qty`
  物理在手库存
- `available_qty`
  可售库存，可用于新订单锁定
- `locked_qty`
  已锁定但尚未正式扣减的库存

关系建议：

```text
on_hand_qty >= available_qty + locked_qty
```

在一期简化模型下，可以通过统一服务保证数值变化，不强依赖复杂库存类型拆分。

### 4.2 库存相关业务动作

库存域一期至少支持以下动作：

- 查询可售库存
- 锁定库存
- 释放锁定库存
- 出库扣减库存
- 记录库存流水

## 5. 一期分仓策略

### 5.1 总体策略

一期采用 `单仓优先、规则清晰、易于落地` 的分仓策略。

订单审核通过后，系统按订单明细逐行选择一个履约仓，并执行锁库。

### 5.2 基础分仓规则

建议一期按以下顺序选择仓库：

1. 过滤掉停用仓库
2. 过滤掉不具备 SKU 可售库存的仓库
3. 如后续有区域覆盖配置，则优先匹配客户收货区域
4. 按仓库优先级升序选择
5. 选择第一个能满足该明细需求数量的仓库

### 5.3 一期分仓边界

一期明确采用以下限制：

- 一个订单明细行默认只分配一个仓库
- 单仓无法满足时，不自动拆成多仓履约
- 单仓无法满足时，先进入 `LOCK_FAILED` 或 `库存不足` 处理
- 多仓拆单能力留到后续迭代

这种做法的好处是：

- 业务语义清楚
- 实现复杂度可控
- 后续能自然升级到“主单 + 子单 + 履约明细”

## 6. 库存锁定流程

### 6.1 触发时机

建议在 `订单审核通过` 后立即触发锁库，而不是在下单时直接占库存。

这样做的原因：

- 更符合 B2B 人工审核场景
- 可避免大量无效订单长时间占用库存
- 便于将审核结果与履约动作解耦

### 6.2 锁库流程

正常流程建议如下：

1. 获取订单和订单明细
2. 校验订单当前状态为 `PENDING_LOCK`
3. 针对每个订单明细执行分仓候选计算
4. 选择目标仓库
5. 校验目标仓 `available_qty >= order_qty`
6. 更新库存：
   `available_qty -= lock_qty`
   `locked_qty += lock_qty`
7. 写入 `sc_inventory_lock`
8. 写入 `sc_inventory_log`
9. 更新订单明细的 `warehouse_id`、`locked_qty`
10. 全部明细成功后，推进订单进入 `PENDING_OUTBOUND`

### 6.3 锁库原子性建议

一期建议以“订单级锁库成功或失败”为原则：

- 任一明细锁库失败，则整个订单锁库失败
- 已成功锁定的明细要回滚释放
- 订单状态统一进入 `LOCK_FAILED`

这样可以避免一期就引入“部分成功、部分失败”的复杂履约状态。

## 7. 锁库失败处理

### 7.1 常见失败原因

- 仓库库存不足
- SKU 在所有候选仓都不可售
- 仓库停用
- 并发下可售库存已被其他订单占用
- 订单状态已被其他流程变更

### 7.2 失败后的处理动作

锁库失败后建议执行：

1. 回滚已成功锁定的明细
2. 写库存流水，类型为 `LOCK_RELEASE`
3. 订单主状态改为 `LOCK_FAILED`
4. 写订单轨迹
5. 记录失败原因，供后台人工查看

## 8. 库存释放规则

### 8.1 释放触发场景

一期建议在以下场景释放锁定库存：

- 订单取消
- 锁库中途失败回滚
- 审核后人工关闭订单

### 8.2 释放流程

1. 查询订单下所有 `LOCKED` 状态的锁定记录
2. 对应库存执行：
   `available_qty += lock_qty`
   `locked_qty -= lock_qty`
3. 将锁记录更新为 `RELEASED`
4. 写库存流水
5. 写订单轨迹

### 8.3 释放幂等要求

释放库存时必须防止重复释放：

- 锁定记录状态从 `LOCKED` 才允许变更为 `RELEASED`
- 重复请求时，若锁状态已不是 `LOCKED`，则直接忽略或视为幂等成功

## 9. 出库扣减规则

### 9.1 扣减时机

一期建议在“出库完成”时进行正式库存扣减。

原因：

- 锁定只代表库存预占
- 出库完成才代表库存真正离库

### 9.2 扣减流程

出库完成后，对对应锁定记录执行：

- `locked_qty -= outbound_qty`
- `on_hand_qty -= outbound_qty`

同时：

- 锁记录状态从 `LOCKED` 更新为 `DEDUCTED`
- 写库存流水，类型为 `OUTBOUND_DEDUCT`

### 9.3 扣减边界

一期默认不支持部分出库：

- 一个订单明细锁多少，默认就出多少
- 若后续支持部分出库，需要在 `outbound_item` 维度扩展实际出库数量控制

## 10. 关键数据对象职责

### 10.1 `sc_inventory`

职责：

- 保存仓库 SKU 当前库存快照

核心关注点：

- 数量口径统一
- 支持并发更新

### 10.2 `sc_inventory_lock`

职责：

- 保存订单与库存之间的锁定关系

核心关注点：

- 哪个订单
- 哪个明细
- 锁了哪个仓
- 锁了多少
- 当前锁状态是什么

### 10.3 `sc_inventory_log`

职责：

- 保存库存流水

建议一期至少覆盖以下 `biz_type`：

- `LOCK`
- `LOCK_RELEASE`
- `OUTBOUND_DEDUCT`
- `MANUAL_ADJUST`

## 11. 服务拆分建议

### 11.1 `InventoryDomainService`

职责：

- 查询库存
- 执行锁库
- 执行释放
- 执行扣减

### 11.2 `WarehouseAllocationService`

职责：

- 根据订单明细计算候选仓
- 选择目标仓
- 返回分仓结果

### 11.3 `InventoryLogService`

职责：

- 封装库存流水落库

### 11.4 `OrderInventoryOrchestrator`

职责：

- 作为订单审核通过后的库存编排入口
- 串联分仓、锁库、状态推进、回滚

## 12. 与订单状态机的配合

库存与分仓流程建议映射到以下状态变化：

- 审核通过：
  `PENDING_AUDIT -> PENDING_LOCK`
- 锁库成功：
  `PENDING_LOCK -> PENDING_OUTBOUND`
- 锁库失败：
  `PENDING_LOCK -> LOCK_FAILED`
- 取消释放：
  已锁库订单进入 `CANCELED`
- 出库扣减后：
  履约状态推进到出库或待发货阶段

## 13. 一期异常与补偿建议

### 13.1 锁库异常

建议处理：

- 订单级事务内失败直接回滚
- 若涉及远程调用，后续可通过 MQ 或补偿任务增强

### 13.2 出库扣减异常

建议处理：

- 出库单完成与库存扣减保持同一事务边界
- 若失败，则不允许订单进入下一状态

### 13.3 重复执行

建议处理：

- 锁库、释放、扣减都要有状态校验
- 关键动作加幂等校验，防止任务重试导致重复处理

## 14. 一期不做但要预留的方向

- 多仓拆单
- 同一明细拆分到多个仓
- 仓库区域配送范围精细化
- 仓间调拨
- 库存预警和自动补货联动
- 采购回补占用逻辑
