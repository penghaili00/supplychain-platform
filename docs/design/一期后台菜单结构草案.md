# B2B 供应链订单履约平台一期后台菜单结构草案

## 1. 文档目标

本文档用于定义一期后台管理端的菜单层级和权限骨架。

当前目标不是把所有页面和按钮细节一次性补全，而是先把后台菜单主结构定清楚，保证后续：

- 模块划分不发散
- 权限编码有统一命名规则
- 后台页面和接口开发可以围绕同一套菜单骨架推进

## 2. 当前结构判断

结合现有一期范围和当前工程结构，一期后台最适合先围绕以下几块建设：

- 工作台
- 客户中心
- 商品中心
- 仓库库存
- 订单履约
- 系统管理

这套结构能覆盖一期主链，又不会过早把采购、财务、售后铺得太散。

## 3. 当前项目结构优化说明

本次已顺手清理 `supplychain-service-provider` 下几个空的旧脚手架目录：

- `entity`
- `mapper`
- `service`
- `dubbo`

保留按业务域组织的结构更适合当前项目，比如：

- `customer`
- `product`
- `inventory`
- `warehouse`
- `order`
- `fulfillment`
- `shipment`
- `rbac`
- `audit`

后续新增代码建议继续按“业务域 -> entity / mapper / service / dubbo”这种方式展开，不再回到根目录平铺。

## 8. 对当前 `sys_menu` 的结构建议

当前项目里的 `sys_menu` 还偏“权限点表”，字段较少，只够支撑基础权限控制。

如果后续要真正承载后台菜单树，建议在后续迭代时补以下字段：

- `parent_id`
- `menu_type`
- `route_path`
- `component_path`
- `icon`
- `sort`
- `visible`

这样才能同时支撑：

- 菜单树展示
- 页面路由
- 按钮权限点

一期如果暂时不做完整后台前端，也可以先按本草案维护“菜单层级 + 权限编码”，等后面再扩表。

## 9. 一期建议先落哪些菜单

如果要控制节奏，建议先按这个顺序落菜单：

1. `系统管理`
2. `客户中心`
3. `商品中心`
4. `订单履约`
5. `仓库库存`

原因：

- 先有 RBAC 骨架
- 再有主数据菜单
- 最后接订单和履约菜单
